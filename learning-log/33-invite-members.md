# Q2. The expires_at filter (AND expires_at > NOW()) appears in findPendingInvitation. If an expired invitation row exists for a given email, a new invitation can be sent. Trace through the accept-invitation logic (as you expect it to work in Chapter 34) and state the outcome.

Tracing through what accept-invitation would likely do (Chapter 34)

Invitee submits the old, expired raw token.
The server hashes it: SHA-256(oldRawToken).
It looks up the invitations table using something like:

sql   SELECT * FROM invitations
   WHERE token_hash = $1 AND expires_at > NOW()

Even though a row exists with that exact hash, the expires_at > NOW() condition fails, because it already expired.
The query returns nothing — same as if the token never existed at all.
The accept-invitation handler treats this as "invalid token" → probably returns a 400 or 404-style error, something like "Invalid or expired invitation."

A safer alternative: a dedicated "transfer ownership" action
Instead of touching the invite system at all, build a separate, explicit endpoint just for this:
POST /api/companies/transfer-ownership
{ "newOwnerUserId": "..." }
Rules this dedicated action should enforce:

Only the current owner can call it.
The target must already be an existing member of the company (not a random outsider — so this doesn't bypass the invite system's email-verification safety at all).
It should be a single atomic step: the old owner's role changes to something else (like hr_manager), and the new person's role changes to owner — both at once, so there's never a moment with two owners or zero owners.
Ideally require a confirmation step (e.g., "are you sure?" or even an email confirmation), since this is a high-stakes, hard-to-undo action.
